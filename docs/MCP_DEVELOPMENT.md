# Fender Studio Pro MCP 개발 절차

## 작업 단위를 고른다

새 플러그인은 사용자가 할 수 있게 만들 동작부터 정한다. 예를 들어 특정 모델 두 개 교체, 특정 파일 형식의 프리셋 적용, 지정한 출력 경로 변경은 각각 검증할 수 있는 단위다. 기존의 미완료 작업을 이어갈 때는 [재개 안내](RESUME.md)를 따른다.

- 제품과 플러그인 버전, 형식, 앱 버전과 빌드, 운영체제와 아키텍처를 확인한다. macOS Apple Silicon의 VST3를 먼저 검증한다. AU, Windows, 다른 앱 빌드의 지원 여부는 각각 확인한다.
- 같은 기능의 기존 도구와 [검증 기록](VALIDATION.md) 및 `docs/evidence/`에서 해당 사례를 찾는다. 쓰기 전에 성공 기준과 영향을 받으면 안 되는 설정, 원복 방법을 정한다.
- 설치된 제조사 공식 배포본을 사용한다. 필요할 때 플러그인의 서명, 클래스 ID와 바이너리 식별자를 대조한다. 제품명만 같은 다른 형식이나 버전은 별도의 시험 대상으로 잡는다.

## 호스트에서 쓸 제어 경로를 고른다

1. 제조사 문서, 플러그인 SDK, 호스트가 제공하는 파라미터·프리셋·상태 인터페이스를 확인한다. `plugin_inspect`, `plugin_parameters`, `plugin_parameter_set`의 읽기 확인, `plugin_state`로 처리할 수 있는 범위를 먼저 대조한다.
2. 공통 경로로 확인할 수 없는 동작은 제조사 공식 배포본을 대상으로 REA, Ghidra, Craft-Anything에서 조사한다. Craft-Anything에서는 조사 전용으로 대상을 열고, 바이너리 내부를 볼 때는 Deep 모드에서 파일 구성·문자열·호출 관계를 살핀다. REA·Ghidra의 관측과 대조하고, 가능한 경우 격리한 SDK 시험으로 입출력과 복원을 확인한다. [Craft-Anything 공식 사용 안내](https://github.com/storytold/craft-anything#two-ways-to-use-it)
3. Rust에서 공통 검증과 타입을 재사용한다. 제품 전용 프리셋이나 동작은 공통 도구의 제품별 처리로 추가할 수 있는지 확인한다. 정확한 버전·클래스·인스턴스와 허용된 입력에 묶는다. 호스트의 네이티브 경로에는 검증된 빌드 또는 ABI 조건을 적용한다. [브리지와 네이티브 호출 구조](ARCHITECTURE.md)

## 실제 앱에서 변경과 복원을 확인한다

1. 현재 브리지·네이티브 설치, Studio Pro 프로세스와 제어권, 장치 연결을 확인한다. 새로 이름 붙인 시험곡에 정확한 대상 인스턴스를 삽입한다. 시험에 쓰는 세션·문서·인스턴스를 다시 확인하고 단일 MCP 프로세스만 사용한다.
2. 변경 전 파라미터 또는 그래프를 읽는다. 파라미터는 화면 이름과 클래스·태그·타입을 함께 기록하고 원래값과 정규화 값을 대조한다. 모델과 프리셋을 바꾸면 파라미터 구성이 달라질 수 있으므로 두 상태의 구성을 각각 기록한다. 다른 인스턴스나 다른 슬롯을 잘못 바꿀 수 있는 동작은 피어 하나를 두고 함께 읽는다.
3. 요청을 한 번 보내고 같은 문서·인스턴스에서 독립적으로 다시 읽는다. 명령 접수, 독립 읽기로 확인한 결과, 알 수 없는 결과를 구분해 기록한다. 지연 뒤 값이 달라지는 경우도 기록한다. 화면에서 확인할 수 있는 이름·순서·동작은 화면을 대조한다. 응답이 끊겨 결과를 모를 때는 추가 쓰기를 멈추고 실제 상태부터 확인한다.
4. 지원을 주장하는 범위에 맞게 시험한다. 쓰기 가능 파라미터 전체는 각 값의 변경·독립 읽기·복원을 확인한다. 프리셋은 파일 형식과 버전마다 시험한 대표 파일을 기록한다. 전체 파일을 시험했다면 파일 수를 따로 기록한다. 모델, 프리셋, MIDI, 편집기 전용 버튼, 중첩 그래프는 해당 기능이 있는 경우 각각 검증한다.
5. 원래 값을 복원하고 전체 관련 값과 상태 지문을 대조한다. 읽기 전용 미터나 동적으로 표시되는 값은 관찰 범위를 명시한다. 저장 지속성은 소유한 시험곡을 저장하고 앱을 재시작해 새 세션에서 확인한다. 되돌리기는 앱의 기록과 전체 원복을 확인한다. 물리 오디오, MIDI, CV는 필요한 장치를 연결한 상태에서 별도로 검증한다.
6. 저장 시험을 제외한 시험곡은 저장 없이 닫는다. 토큰과 제어권을 해제하고 시험 프로세스를 종료한다. 진단용 설치나 설정을 바꾼 경우 평소 상태와 다시 대조한다.

## 다음 채팅에 필요한 근거를 남긴다

- 공개 근거는 `docs/evidence/`에 기존 형식을 따라 추가한다. 대상 버전과 범위, 요청과 독립 관측, 원복과 정리, 재현에 필요한 전제, 남은 한계를 남긴다. 사용자 데이터와 제조사 리소스 원본은 로컬에 보존한다. 실패 이유와 이전 시험에서 이미 확인한 내용은 날짜별 인수인계에 기록한다.
- 진행 보고는 사용자에게 한국어로 짧게 쓴다. 각 단위의 실제 시간, 고정 대기열의 완료와 잔여 수, 다음 단위와 전체 예상, 현재 종료 시각까지 남은 시간을 함께 적는다. 새로 발견한 범위는 예상이 달라진 이유와 함께 기록한다. 추정할 근거가 부족한 연구와 장비 대기는 별도로 표시한다.
- 재개 지점은 상태 파일과 최신 날짜별 인수인계에 남긴다. 마지막 완료 단위, 다음 동작, 실제 앱·설치 정리 상태, 열린 PR과 확인할 검사를 적는다. 다음 채팅은 이 항목과 필요한 근거 파일부터 읽는다.

## 검증된 단위를 각각 병합한다

[기여 안내](../CONTRIBUTING.md)의 오프라인 검사와 네이티브 검사 절차를 따른다. 플러그인 동작에는 해당 범위의 실앱 근거를 붙인다. 한 단위가 독립적으로 쓸 수 있는 상태가 되면 그 단위의 PR을 연다. `Core offline checks`와 `macOS arm64 native checks`가 최신 `main`을 반영한 정확한 PR 헤드에서 통과하면 바로 병합하고 원격 `main`에서 결과를 확인한다.
