# 2026년 11월 24일 재개 기록

11월 24일 오전 1시 11분에 사용자 지시로 재개했다. 오전 6시 이동 일정에 맞춰 오전 5시 45분부터 새 실앱 검증을 열지 않는다. 실행 중인 시험의 정리와 설치 원복, GitHub 확인, 인수인계 기록에 남은 시간을 쓴다. 시간은 한국 시간이다.

## 이전 실행 중단과 복구

- 11월 21일 오전 4시 39분 32초에 Codex의 응답 API가 HTTP 400 `Bad Request`로 끝났다. 작업 종료 이벤트와 HTTP 클라이언트 기록에 같은 응답을 확인했다. 응답 본문에는 이 문구만 들어 있어 서버가 거부한 세부 이유는 확인할 수 없다.
- 당시 Studio Pro 8.1.1은 Saturn 2의 `FS2a` 버전 4를 검증한 상태였다. R232에서 `Clean Tape Base - 4 Bands SM` 및 네 밴드 표시를 확인했고, 45개 값이 바뀐 뒤 전체 1,088개 값과 컴포넌트 지문을 복원했다. Studio Pro와 MCP는 정상 종료했고 화면에서 저장을 거부한 것을 확인했다. 요청 182회·174.383초, 앱 실행부터 종료까지 269.748초였다.
- 종료 뒤 실행할 마무리 절차와 네 번째 프리셋 시험은 남아 있었다. 재개 직후 기존 R232 검증 증거와 현재의 설치 파일 18개가 당시 시험용 상태와 일치하는지 확인했다. R232 종료 기록을 확정하고 플러그인 시작 안내 설정, 프리셋 폴더 84개 항목과 정상 설치 파일 18개의 내용 및 권한을 복원했다. R230과 R231의 완료한 시험은 다시 실행하지 않았다.
- 마지막으로 공개된 변경은 콘솔 선택 조회 [PR #73](https://github.com/dev-universe/fender-studio-pro-mcp/pull/73)이었다. 두 필수 검사가 통과한 헤드 `eb8d399`를 `main` 커밋 `7bd49e3`에 병합했다.

## 현재 실행과 기존 대기열

내장 43개 중 18개 완료, 25개 잔여다. 장비가 필요한 4개는 Volt 276, Keystation88 MK3 및 물리 루프백 배선이 필요한 경우를 포함한다. 이번 시작 시 두 장치가 감지되지 않았다. FabFilter 제조사 파일 적용은 6/23종, 전수 파라미터 시험은 쓰기 가능한 12,455개 중 12,448개다. 현재 소프트웨어 잔여 기간은 2~5일로 추정한다. 오늘의 실제앱 종료 시각은 이 추정과 별개다.

### Saturn 2 제조사 파일 적용 완료

- R229에서 공식 VST3 2.13의 제조사 파일 77개를 형식별로 분류하고 REA·Ghidra의 호출 경로와 별도 VST3 SDK 실행을 대조했다. `FS2a` 버전 2·3·4와 `FSat` 버전 4에서 64·162·47·15개가 바뀌었다. 네 경우에 보고된 값 1,088개와 처리부·컨트롤러의 상태를 원복했다. 없는 파일은 오류 `-1`을 반환했고 부수 변경은 관찰되지 않았다.
- 실제 8.1.1 빌드 113103에서 R230 `Brutal Compressor bM`, R231 `Magic bM`, R232 `Clean Tape Base - 4 Bands SM`, R233 `Old Tape Crunch SM`을 각각 한 번 적용했다. 화면과 독립 읽기에서 변경값 58·164·45·11개를 관찰했다. 네 경우에 남은 내부값 `vstp1073741826`을 별도로 보정해 전체 1,088개와 컴포넌트 지문을 원복했다. 이전 카탈로그 및 문서, 다른 인스턴스, 닫힌 편집기는 거부했다. 각각 182요청이었고 R233은 요청 실행 120.054초, 앱 실행부터 종료까지 186.149초다. R233은 저장 없이 닫았고 프리셋 트리 84개 및 환경설정·설치 파일 18개의 기준을 복원했다.
- 검증한 코드는 [PR #74](https://github.com/dev-universe/fender-studio-pro-mcp/pull/74)의 헤드 `9c8ce20`에서 두 필수 검사를 통과했다. 11월 24일 오전 1시 30분에 공개 `main`의 `80f1ea9`에 병합했으며 예상 병합 파일 트리와 일치했다.

### Impact 주 출력 복구 경로 R234와 R235

- R234에서 `getDestinationChannel()`을 실제 Impact 편곡 트랙의 세 시점에서 읽었다. 시작, `St 1` 제거, `St 1` 재생성 시점에 모두 `null`이었다. 출력 32개와 DSP 4,262개를 확인했다. 화면과 콘솔 읽기의 선택은 `St 1 → St 2 → St 2`였고 편곡 트랙은 선택 상태를 유지했다. 녹음 대기와 모니터는 모두 꺼져 있었다. 204요청·97.266초, 앱 실행부터 종료까지 130.906초다. 검증 범위상 이 조회를 Impact 연결 판정에 사용할 근거가 없어 실험 브랜치에 보존했다.
- R235는 Ghidra에서 확인한 콘솔 채널 스크립트의 `focus()`를 재생성한 `St 1`에 한 번 요청했다. 문서, 세션, 악기 인스턴스, 선택된 빈 편곡 트랙, 출력 32개, 음소거 상태와 녹음 대기·모니터를 대조한 뒤 호출했다. 수신 응답은 `requested: true`였다. 화면과 MCP 독립 읽기 모두 `St 2` 선택이 그대로였고 편곡 트랙 선택과 녹음 대기·모니터, 믹서, 출력 32개와 DSP 4,262개도 유지됐다. 243요청·98.816초, 앱 실행부터 종료까지 223.232초다. 시험 곡을 저장하지 않았고 설치 파일 18개의 내용과 권한을 복원했다. 이 경로는 주 출력 선택 복원에 효과가 관찰되지 않아 공개 명령으로 추가하지 않았다.
- Impact의 다음 조사에서는 주 출력과 편곡 트랙 사이의 연결을 다시 연결하는 경로와 일반 콘솔 선택 동작을 구분한다. R234의 조회와 R235의 `focus()`를 같은 구성에서 반복할 필요가 없다. 주 출력이 재생성되는 동안 `St 1`의 색상, 실제 선택, 편곡 트랙 선택 및 녹음 대기·모니터가 함께 복원되기 전까지 이 단위를 완료로 집계하지 않는다.
