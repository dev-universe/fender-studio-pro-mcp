## 이전 실행 중단과 복구

- 11월 21일 오전 4시 39분 32초에 Codex의 응답 API가 HTTP 400 `Bad Request`로 끝났다. 작업 종료 이벤트와 HTTP 클라이언트 기록에 같은 응답을 확인했다. 응답 본문에는 이 문구만 들어 있어 서버가 거부한 세부 이유는 확인할 수 없다.
- 당시 Studio Pro 8.1.1은 Saturn 2의 `FS2a` 버전 4를 검증한 상태였다. R232에서 `Clean Tape Base - 4 Bands SM` 및 네 밴드 표시를 확인했고, 45개 값이 바뀐 뒤 전체 1,088개 값과 컴포넌트 지문을 복원했다. Studio Pro와 MCP는 정상 종료했고 화면에서 저장을 거부한 것을 확인했다. 요청 182회·174.383초, 앱 실행부터 종료까지 269.748초였다.
- 종료 뒤 실행할 마무리 절차와 네 번째 프리셋 시험은 남아 있었다. 재개 직후 기존 R232 검증 증거와 현재의 설치 파일 18개가 당시 시험용 상태와 일치하는지 확인했다. R232 종료 기록을 확정하고 플러그인 시작 안내 설정, 프리셋 폴더 84개 항목과 정상 설치 파일 18개의 내용 및 권한을 복원했다. R230과 R231의 완료한 시험은 다시 실행하지 않았다.
- 마지막으로 공개된 변경은 콘솔 선택 조회 [PR #73](https://github.com/dev-universe/fender-studio-pro-mcp/pull/73)이었다. 두 필수 검사가 통과한 헤드 `eb8d399`를 `main` 커밋 `7bd49e3`에 병합했다.

### External Effect Return 읽기

- R246은 기존 Send의 현재 경로 저장칸과 Return의 실제 연결을 Ghidra에서 구분했다. Return 전용 버스 생성, 첫 연결 읽기 및 입력 연결 변경의 함수가 각각 같은 Return 보유 객체에 이어졌다. 서명된 Studio Pro 8.1.1 빌드 113103의 arm64 조각과 함수 표를 대조했다.
- R248은 별도의 바운드 시험 곡에서 External Effect Stereo 인스턴스 두 개를 삽입했다. Return은 편집기를 열기 전, 연 뒤, 메뉴를 보고 닫은 뒤 모두 미배정이었다. Send도 미배정이었다. 화면과 읽기 전용 MCP 메뉴에는 `없음`과 오디오 I/O 설정만 있었다. 컨트롤러 24개가 같았고 Send와 Return 쓰기는 각각 0회다. 61요청·62.098초, 앱 실행부터 종료까지 157.114초다. 설치 파일 18개를 복원했다. 시험 시작 전 실행기 인자를 고치는 동안 빈 시작 화면이 열려 문서가 없음을 확인하고 닫은 뒤 정확한 시험 곡을 새로 열었다.
- Return 배정 상태의 긍정 검증과 제어·오디오 왕복은 아직 확인하지 않았다. 실제 입력 포트가 있는 다음 시험에서 변경·독립 읽기·원복, 대상과 피어 인스턴스 가드, 오디오 경로를 차례로 확인한다.

R303은 76요청·31.440초, 앱 64.468초였고 빈 상태의 28개 값과 기존 설치 파일 18개를 원복했다.
- R305는 이전 두 드래그와 다른 위치인 Reverb 본체 오른쪽을 시험했다. 화면 순서가 그대로여서 성공 신호를 보내지 않았다. 시험 도구의 같은 단계 키가 두 번 정의돼 중립 확인 문자열을 받을 수 없는 문제도 발견했다. 앞선 owner를 정상 종료하고 같은 문서·세션을 새 읽기 전용 owner로 묶었다. 8요청에서 Pedalboard 40개, Phase Meter, 믹서, 인서트, 타임라인이 준비 시점과 정확히 같았다. 본 시험은 48요청·41.334초, 앱 83.406초, 소유자 둘은 정상 종료했다. 시험곡은 저장하지 않았으며 설치 파일 18개를 원복했다.

### Pedalboard 편집 인터페이스 R306과 유한 교체 R307

| `CONTROL-SCOPE` | 이미 완료한 제한 범위의 캡처·홀드를 재사용하고, 직접 시작·완료, 비활성 매핑 및 숨은 상태를 확인한다. |
| `CONTROL-MULTI` | 중첩 자식 악기와 레이어·라우팅을 편집하고 영향받지 않은 자식을 함께 대조한다. |
| `CONTROL-IMPACT` | 확인한 보조 출력 31개를 재사용한다. 주 출력 재생성과 색상, 콘솔·편곡 선택의 동시 복원 및 패드 제어를 이어간다. |
| `SHARED-GRAPH` | R251·R254·R257의 서브그래프 생성·제거·이동과 재개방 증거를 재사용한다. 일반 연결, 다른 분기 및 삭제 구조를 확인한다. |
| `SHARED-EVENT` | MIDI 이벤트의 눌림·해제 및 종료 계약을 실제 입력과 구분해 시험한다. 작업 중간 실패와 안전한 정리도 확인한다. |
| `SHARED-PERSISTENCE` | 각 구조 변경의 저장·재시작·이전 ID 거부 범위를 확인한다. Pedalboard와 완료된 Splitter 형태는 재사용한다. |
| `SHARED-MACOS-PACKAGE` | 공개 릴리스 자산에서 최초 설치, 갱신, 제거, 이전 설치 복구를 독립된 프로필에서 확인한다. |
| `SHARED-DOCS-RELEASE` | 검증 범위를 README와 지원표에 연결하고 필수 검사를 통과한 각 PR을 즉시 병합한다. |
| `SHARED-PHYSICAL-KEYS` | Keystation88 MK3 재연결 후 실제 MIDI 입력과 해제 및 장치 분리 때의 상태를 확인한다. |

이번에 Volt 276과 Keystation88 MK3는 감지되지 않았다. 지난 연결은 USB만 있었으므로 물리 왕복은 출력과 입력의 실제 배선이 필요하다. 나머지 소프트웨어는 장치 없이 병행한다. 사용자가 8.1.1 공식 설치 파일 대조를 생략하라고 했으므로 그 요청을 다시 묻지 않는다.

FabFilter는 제조사 파일 형식별 대표 시험 23종이 끝났다. 남은 7개는 실제 호스트에서 독립적으로 읽을 때 값이 유지되는지를 기준으로 계속 집계한다. 공식 처리부의 피드백 전달 시점과 실제 호스트의 독립 읽기 계약을 대조하고, 사용자 조작에 대응하는 별도의 공개 컨트롤이 있으면 실제 앱에서 한 가지씩 검증한다. 현재 소프트웨어 예상 2~5일은 남은 연구의 범위에 대한 추정이다. 실제 장치 일정과 공개 저장소의 CI 대기 시간은 별도다.


### 다음 Pedalboard 실앱 시험의 판정 기준

현재 공개 후보는 한 번의 인접 교체만 요청한다. Ghidra에서 두 슬롯의 효과 클래스가 같으면 두 기존 효과의 상태를 다시 불러오는 분기와, 클래스가 다르면 각 위치의 효과를 새로 구성하는 분기를 확인했다. R309·R310·R311·R312는 다른 두 클래스다. 아래 시험은 독립된 새 문서에서 한 가지씩 진행한다.

1. 동일 모델 두 개에 서로 다른 노브 값과 활성 상태를 먼저 설정한다. 교체 전후 모델명이 같으므로 각 위치의 정규화 비트, 원래값 종류, 활성 상태, 전체 지문으로 판단한다. 걸러야 할 요청은 같은 슬롯, 다른 인스턴스, 이전 문서, 예상 값 불일치다. 지금 명령의 동일 모델 거부는 새 검증을 마칠 때까지 유효하다.
2. 빈 슬롯 이동은 점유된 기존 슬롯과 비어 있는 대상을 명시하고, 옮긴 뒤 원래 슬롯이 비는지와 페달의 전체 설정 및 나머지 슬롯을 독립 읽는다. 없는 슬롯을 정식 슬롯 ID와 구분한다. 검증 전에는 단일 교체 호출 또는 여러 슬롯을 건너뛰는 호출로 결과를 추정하지 않는다.
3. 비인접 교환과 한 페달의 순차 이동은 결과 순서가 다르다. 서로 다른 모델을 세 개 이상 배치하고 기대 순서를 요청 전에 고정한다. 구분선 전후에 걸치는 경우에는 `stompOrder`와 각 부분의 순서도 따로 대조한다. 실제 두 채널을 쓰기 전에 재생을 멈추고 시험 채널과 Main을 확인한다.
4. 앱의 되돌리기 검증은 R312처럼 교체 전 맨 위 항목, 교체 직후 새 항목, 한 번의 실행 취소, 전체 복원 순으로 검증한다. 저장은 소유한 복제본에서 한 번만 수행하며, 새 프로세스의 독립 읽기와 세션 바인딩까지 확인한다.
