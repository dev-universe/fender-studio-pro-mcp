## CV 콘솔 실측

- Shift를 누르고 8.1.1을 시작했지만 복구 화면 대신 MIDI 재연결 안내가 떴다. VST 스캐너가 시스템 폴더 후보를 열거했다. 곡을 열기 전에 그 프로세스를 닫았다.
- 다음 시도에서는 Studio Pro와 그 하위 프로세스가 시스템 플러그인 폴더와 기존 사용자 플러그인 폴더를 읽거나 실행하지 못하도록 제한했다. 전역 경로의 두 표기에서 접근 거부를 재현했고, 당시 VST 스캐너 후보는 0개였다.
- Native59와 이름을 지정한 복사본 Scratch에서 콘솔 왼쪽 그룹 패널이 비어 있는 것을 확인했다. 시작 시 편곡 창에 포커스가 있었고 Surround Panner 트랙이 선택돼 있었다. 그룹 패널을 열 때 콘솔 포커스 표시가 켜졌다.
- 가로 스크롤로 56번 CV 오디오 채널을 화면에 표시했다. 채널 라벨 우클릭은 색상 팔레트를 열어 Escape로 닫았다. 채널 본체 우클릭은 그룹 할당 메뉴를 표시하는 대신 CV 채널을 선택했다. 선택과 함께 CV의 녹음 준비와 모니터가 켜졌고, Mojito 10의 두 값은 꺼졌다. 실제 API에서 앞뒤 67개 채널을 읽어 확인했다. 채널별 뮤트와 솔로를 포함해 두 채널의 이 네 필드 외에는 변화가 없었다. 뮤트는 각 스냅샷에서 49개, CV 뮤트는 0이었다.
- 첫 MCP 스냅샷 도구는 공백이 있는 파일 URL을 문자 그대로 비교해 이름이 정확한데도 문맥 단계에서 멈췄다. 두 번째 별도 owner에서 URL을 정규화하되 정확한 로컬 파일 경로와 제목을 비교했다. 새 owner에서 읽기 요청 7개를 완료했다. MCP 뮤트 쓰기와 Native60 lifecycle 호출은 0회다.
- Scratch를 닫고 복사본과 보호 파일 13개를 해시로 확인했다. 제한된 Studio Pro 프로세스는 이 실행의 종료 과정에서 비정상 종료 코드 139와 우클릭 처리 스택을 남겼다. 원인과 이벤트 인과관계는 확정하지 못했다. 당시 별도 프로세스로 다시 열린 앱도 곡이 없는 상태에서 종료했다.

그룹 패널과 뮤트 상태를 확인했다. 그룹 할당 서브메뉴와 Control Link의 새 CV 뮤트 값은 이 단위에서 직접 읽지 못했다. 무엇보다 채널 본체 클릭은 믹서 포커스를 줄 때 안전한 중립 영역이 아니다. 다음 CV 실기에서 이를 같은 준비 동작으로 반복하지 않는다. 이전 R83과 R85의 뮤트 실패 원인은 미확정이며 Native60은 그대로 초안이다.

## 공식 FabFilter 바이너리와 호스트 연결

설치 목록의 VST3 23개와 같은 버전의 FabFilter 공식 서명본을 사용했다. 독립 이진 분석은 577.290초가 걸렸다. 22개를 새로 분석했고 Pro-Q 4는 arm64 파일 해시와 공개 심볼 위치가 같아 기존 증거를 재사용했다. 전체 23개에서 Apple 인증서 체인과 FabFilter 배포자, arm64 공개 팩토리와 모듈 시작·종료 심볼을 확인했다. 첫 분기의 실제 대상은 원래 바이트, REA·Ghidra와 Craft Anything을 대조했다. 이 결과는 퍼블릭 VST3 API 경계에 대한 증거다.

시스템 폴더 접근을 제한한 8.1.1에 서명이 일치하는 공식 Pro-Q 4.13과 Twin 3.10만 임시 사용자 VST3 폴더로 제공했다. VST 스캔 후보는 정확히 2개였다. [PR #8](https://github.com/dev-universe/fender-studio-pro-mcp/pull/8)의 클래스 ID 선택 코드를 사용했다. 두 제품은 캐시에 표시 이름이 같은 AU 클래스도 보였다. `tracks_edit`가 선택한 VST3 클래스는 삽입 뒤 Native59의 인스턴스 클래스 및 실제 호스트 프로세스에 매핑된 공식 파일 해시와 일치했다. 시스템 전체를 대상으로 기존 설치본을 교체하지 않았다.

Pro-Q 4는 `vstp2`의 정규화 값 약 0.57518846을 약 0.60000002로 변경한 뒤 정확히 복원했다. Twin 3는 `vstp0`의 0.5를 약 0.51999998로 변경한 뒤 정확히 복원했다. 두 검사 모두 별도 읽기에서 같은 인스턴스를 확인했다.

## 프리셋 결과와 원복 한계

처음 읽은 호스트 프리셋 목록에는 두 제품 모두 발급받을 항목이 0개였다. FabFilter 자체 에디터에서 제조사 프리셋을 적용했다. 메뉴에서 사용한 두 파일은 공식 패키지의 같은 이름 원본과 일치했다. 이어서 Studio Pro에서 고유 이름의 임시 `.preset` 두 개를 만들고 현재 호스트 카탈로그의 토큰과 발급 인덱스로만 다시 적용했다. 이 경로는 FabFilter 자체 프리셋 목록을 MCP가 직접 열거하거나 불러오는 근거와 구분한다.

Pro-Q 4의 제조사 프리셋 적용 후 캡슐 복원은 호스트가 수락했다. 그러나 다시 읽은 736개 중 `vstp1073741826` 한 개가 원래 값 0으로 돌아오지 않았다. 새 Scratch의 호스트 프리셋 적용에서도 같은 내부 항목 하나가 저장 시점과 달랐다. 735개 일치와 전체 상태 불일치를 함께 남긴다. 두 Scratch를 저장하지 않고 닫았고, 임시 호스트 프리셋 파일은 원본을 건드리지 않고 검증 폴더로 옮겼다.

Twin 3는 제조사 프리셋과 호스트 프리셋 적용을 모두 독립 읽기로 확인했다. 임시 호스트 프리셋을 만든 뒤 대표 값을 변경하고 발급 토큰으로 불러왔을 때 저장 기준 1,509개가 모두 일치했다. 이 검증은 대표값 변경과 호스트 프리셋 결과를 포함한다. 모든 파라미터를 하나씩 쓰거나 실제 오디오 및 재시작 지속성을 확인하지 않았다.

## 기존 대기열에서 병행한 조사

SHARED-GRAPH에서 11월 18일의 완료된 소유권 관측을 재실행하지 않았다. 보존한 Ghidra 작업을 사용해 DeviceEnvironment 할당 래퍼와 연관 객체 필드 접근 두 함수를 17.449초에 읽었다. 다음 생성자 한 개를 13.675초에 읽어 생성된 객체와 registry 호출의 관계를 좁혔다. 읽은 함수만으로 소유권, 살아 있는 엔드포인트 또는 그래프 편집 권한을 구별할 수 없다. 새 쓰기 경로를 추가하지 않았고 내장 완료 수를 올리지 않았다.

첫 registry helper도 12.916초에 확인했다. 생성자에서 전달받은 정확한 포인터를 배열에 넣고 개수를 늘린다. 이 함수에서 직접 retain이나 소유자 판정은 발견하지 못했다. 다음 후보는 생성자가 같은 객체를 넘긴 두 번째 helper다.

## 나머지 FabFilter 21개 공통 경로

이름을 지정한 새 R3 Scratch와 같은 후보 코드에서 나머지 21개를 검증했다. 스캔 후보는 모두 공식 서명본이며 준비한 23개 사용자 번들과 정확히 일치했다. 먼저 Micro 한 개를 실행했고 나머지 20개를 한 owner에서 이어갔다. Micro 검증 구간은 1.536초였고 나머지 묶음은 owner 준비와 정리를 포함해 43.756초였다.

- 제품마다 별도 트랙을 만들고 현재 카탈로그의 정확한 클래스 ID를 사용했다. host가 실제 로드한 각 파일을 서명 검증한 번들의 실행 파일과 대조했다.
- 전체 범위 23개에서 현재값 12,478개를 모두 읽었다. 각 제품에서 확인한 하나의 쓰기 가능 값은 개별 변경과 별도 읽기 뒤 정확히 돌아왔다.
- 이번 21개는 대표 변경 전과 원복 뒤 쓰기 가능 값 10,210개 전체가 일치했다. 이 비교는 한 대표값을 바꾼 뒤 대상과 다른 값까지 보존됐다는 뜻이다.

버전별 결과는 [23개 실제 삽입·대표값 근거](evidence/2026-11-20-fabfilter-actual-representative.json)를 참조한다. 이 묶음의 프리셋 동작은 0회였다.

## FabFilter 자체 프리셋의 공개 프로그램 경로

두 기준 제품의 공식 별도 검사에서 MIDI 이벤트 입력 버스 0과 프로그램 목록 0을 읽었다. 목록에 프로그램 슬롯 128개가 있으며 검사 당시 프로그램 이름은 비어 있었다. 공개 MIDI 매핑은 Bank Select MSB와 LSB에 각각 별도 ID를 반환했다. 프로그램 변경 제어는 127단계의 전용 파라미터를 공개한다. Studio Pro 쪽에서도 해당 ID를 확인했지만 같은 표시명이 여러 행에 있다. 이 정보로 실제 프리셋 번호나 성공을 추정하지 않는다.

다음에는 팩토리 프리셋 메뉴가 표시하는 번호와 옵션을 먼저 확인한다. 같은 제품에서 Bank Select와 Program Change가 의도한 인스턴스에 전달되는 것을 검증한다. 프리셋 이름과 파라미터 변화, 원복을 따로 기록한다. 이 경로가 닫히기 전까지 제조사 `.ffp`를 MCP가 직접 불러온 흔적으로 설명하지 않는다. 현재 검증된 적용 경로는 Studio Pro가 발급한 `.preset` 항목이다.

기존 CV, 그래프와 기타 내장 작업은 11월 18일의 28개 ID 기준으로 이어간다.

## 호스트 프리셋 23개 시험과 공개 병합

R3의 21개는 각 버전의 확인된 인스턴스에서 Studio Pro 프리셋을 고유 이름으로 저장했다. 저장 후의 전체 기준값을 독립 읽기로 확인했다. 대표값 한 개를 변경하고 별도 읽기로 변화가 있었는지 확인한 뒤, MCP에서 발급한 카탈로그 토큰과 인덱스로 프리셋을 한 번 불러왔다. 새 전체 읽기에서 쓰기 가능 값 10,210개가 모두 일치했다. 카탈로그 해제도 21개 모두 확인했다. 719개 요청, 시험별 경과 시간 합계 362.786초였다.

Twin 2 첫 시도는 선택된 악기 트랙이 필요하다는 읽기 거절에서 멈췄다. 쓰기 요청은 0개였다. 유한 CLI 작업으로 정확한 트랙을 선택하고 독립 읽기로 단일 선택을 확인한 새 연결에서 통과했다. One도 같은 선택 조건으로 통과했다. 남은 개선은 이 선택 작업을 이름 있는 MCP 도구로 제공하는 것이다.

앞선 두 시범 제품을 포함해 23개 전체를 시도했다. Studio Pro 프리셋은 22개가 통과했다. Pro-Q 4의 기존 내부 항목 1개 불일치는 해결 대기 상태다. 이 검증과 제조사 프리셋 목록·적용, 개별 쓰기 전수, Save/reopen, 실제 신호 검증은 별도 완료 조건이다. [호스트 프리셋 결과](evidence/2026-11-20-fabfilter-host-presets.json)에 버전별 근거를 정리했다.
