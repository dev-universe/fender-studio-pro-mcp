## CV 콘솔 실측

- Shift를 누르고 8.1.1을 시작했지만 복구 화면 대신 MIDI 재연결 안내가 떴다. VST 스캐너가 시스템 폴더 후보를 열거했다. 곡을 열기 전에 그 프로세스를 닫았다.
- 다음 시도에서는 Studio Pro와 그 하위 프로세스가 시스템 플러그인 폴더와 기존 사용자 플러그인 폴더를 읽거나 실행하지 못하도록 제한했다. 전역 경로의 두 표기에서 접근 거부를 재현했고, 당시 VST 스캐너 후보는 0개였다.
- Native59와 이름을 지정한 복사본 Scratch에서 콘솔 왼쪽 그룹 패널이 비어 있는 것을 확인했다. 시작 시 편곡 창에 포커스가 있었고 Surround Panner 트랙이 선택돼 있었다. 그룹 패널을 열 때 콘솔 포커스 표시가 켜졌다.
- 가로 스크롤로 56번 CV 오디오 채널을 화면에 표시했다. 채널 라벨 우클릭은 색상 팔레트를 열어 Escape로 닫았다. 채널 본체 우클릭은 그룹 할당 메뉴를 표시하는 대신 CV 채널을 선택했다. 선택과 함께 CV의 녹음 준비와 모니터가 켜졌고, Mojito 10의 두 값은 꺼졌다. 실제 API에서 앞뒤 67개 채널을 읽어 확인했다. 채널별 뮤트와 솔로를 포함해 두 채널의 이 네 필드 외에는 변화가 없었다. 뮤트는 각 스냅샷에서 49개, CV 뮤트는 0이었다.
- 첫 MCP 스냅샷 도구는 공백이 있는 파일 URL을 문자 그대로 비교해 이름이 정확한데도 문맥 단계에서 멈췄다. 두 번째 별도 owner에서 URL을 정규화하되 정확한 로컬 파일 경로와 제목을 비교했다. 새 owner에서 읽기 요청 7개를 완료했다. MCP 뮤트 쓰기와 Native60 lifecycle 호출은 0회다.
- Scratch를 닫고 복사본과 보호 파일 13개를 해시로 확인했다. 제한된 Studio Pro 프로세스는 이 실행의 종료 과정에서 비정상 종료 코드 139와 우클릭 처리 스택을 남겼다. 원인과 이벤트 인과관계는 확정하지 못했다. 당시 별도 프로세스로 다시 열린 앱도 곡이 없는 상태에서 종료했다.

그룹 패널과 뮤트 상태를 확인했다. 그룹 할당 서브메뉴와 Control Link의 새 CV 뮤트 값은 이 단위에서 직접 읽지 못했다. 무엇보다 채널 본체 클릭은 믹서 포커스를 줄 때 안전한 중립 영역이 아니다. 다음 CV 실기에서 이를 같은 준비 동작으로 반복하지 않는다. 이전 R83과 R85의 뮤트 실패 원인은 미확정이며 Native60은 그대로 초안이다.

## 공식 FabFilter 바이너리와 호스트 연결

설치 목록의 VST3 23개와 같은 버전의 FabFilter 공식 서명본을 사용했다. 독립 이진 분석은 577.290초가 걸렸다. 22개를 새로 분석했고 Pro-Q 4는 arm64 파일 해시와 공개 심볼 위치가 같아 기존 증거를 재사용했다. 전체 23개에서 Apple 인증서 체인과 FabFilter 배포자, arm64 공개 팩토리와 모듈 시작·종료 심볼을 확인했다. 첫 분기의 실제 대상은 원래 바이트, REA·Ghidra와 Craft Anything을 대조했다. 이 결과는 퍼블릭 VST3 API 경계에 대한 증거다.

시스템 폴더 접근을 제한한 8.1.1에 서명이 일치하는 공식 Pro-Q 4.13과 Twin 3.10만 임시 사용자 VST3 폴더로 제공했다. VST 스캔 후보는 정확히 2개였다. [PR #8](https://github.com/dev-universe/fender-studio-pro-mcp/pull/8)의 클래스 ID 선택 코드를 사용했다. 두 제품은 캐시에 표시 이름이 같은 AU 클래스도 보였다. `tracks_edit`가 선택한 VST3 클래스는 삽입 뒤 Native59의 인스턴스 클래스 및 실제 호스트 프로세스에 매핑된 공식 파일 해시와 일치했다. 시스템 전체를 대상으로 기존 설치본을 교체하지 않았다.

두 버전 모두 공식 [Steinberg VST3 ParameterInfo](https://steinbergmedia.github.io/vst3_doc/vstinterfaces/structSteinberg_1_1Vst_1_1ParameterInfo.html)의 이름과 ID를 실제 호스트 행 전체와 비교했다. 호스트 이름은 `vstp<십진 ParamID>`였고 태그는 ID에 1을 더한 값이었다. 공식 표시 이름은 이미 `params[].native.title`에 있다. 표시 이름이 겹치는 행이 있으므로 setter에는 현재 인스턴스에서 확인한 `params[].name`을 쓴다. 인덱스와 ParamID가 다른 행이 두 제품에 총 337개 있다. 이 식의 일치는 이번 두 버전에서 검증했다.

Pro-Q 4는 `vstp2`의 정규화 값 약 0.57518846을 약 0.60000002로 변경한 뒤 정확히 복원했다. Twin 3는 `vstp0`의 0.5를 약 0.51999998로 변경한 뒤 정확히 복원했다. 두 검사 모두 별도 읽기에서 같은 인스턴스를 확인했다.

## 프리셋 결과와 원복 한계

처음 읽은 호스트 프리셋 목록에는 두 제품 모두 발급받을 항목이 0개였다. FabFilter 자체 에디터에서 제조사 프리셋을 적용했다. 메뉴에서 사용한 두 파일은 공식 패키지의 같은 이름 원본과 일치했다. 이어서 Studio Pro에서 고유 이름의 임시 `.preset` 두 개를 만들고 현재 호스트 카탈로그의 토큰과 발급 인덱스로만 다시 적용했다. 이 경로는 FabFilter 자체 프리셋 목록을 MCP가 직접 열거하거나 불러오는 근거와 구분한다.

Pro-Q 4의 제조사 프리셋 적용 후 캡슐 복원은 호스트가 수락했다. 그러나 다시 읽은 736개 중 `vstp1073741826` 한 개가 원래 값 0으로 돌아오지 않았다. 새 Scratch의 호스트 프리셋 적용에서도 같은 내부 항목 하나가 저장 시점과 달랐다. 735개 일치와 전체 상태 불일치를 함께 남긴다. 두 Scratch를 저장하지 않고 닫았고, 임시 호스트 프리셋 파일은 원본을 건드리지 않고 검증 폴더로 옮겼다.

Twin 3는 제조사 프리셋과 호스트 프리셋 적용을 모두 독립 읽기로 확인했다. 임시 호스트 프리셋을 만든 뒤 대표 값을 변경하고 발급 토큰으로 불러왔을 때 저장 기준 1,509개가 모두 일치했다. 이 검증은 대표값 변경과 호스트 프리셋 결과를 포함한다. 모든 파라미터를 하나씩 쓰거나 실제 오디오 및 재시작 지속성을 확인하지 않았다.

## 기존 대기열에서 병행한 조사

SHARED-GRAPH에서 11월 18일의 완료된 소유권 관측을 재실행하지 않았다. 보존한 Ghidra 작업을 사용해 DeviceEnvironment 할당 래퍼와 연관 객체 필드 접근 두 함수를 17.449초에 읽었다. 다음 생성자 한 개를 13.675초에 읽어 생성된 객체와 registry 호출의 관계를 좁혔다. 읽은 함수만으로 소유권, 살아 있는 엔드포인트 또는 그래프 편집 권한을 구별할 수 없다. 새 쓰기 경로를 추가하지 않았고 내장 완료 수를 올리지 않았다.

첫 registry helper도 12.916초에 확인했다. 생성자에서 전달받은 정확한 포인터를 배열에 넣고 개수를 늘린다. 이 함수에서 직접 retain이나 소유자 판정은 발견하지 못했다. 다음 후보는 생성자가 같은 객체를 넘긴 두 번째 helper다.

## 나머지 FabFilter 21개 공통 경로

이름을 지정한 새 R3 Scratch와 같은 후보 코드에서 나머지 21개를 검증했다. 스캔 후보는 모두 공식 서명본이며 준비한 23개 사용자 번들과 정확히 일치했다. 먼저 Micro 한 개를 실행했고 나머지 20개를 한 owner에서 이어갔다. Micro 검증 구간은 1.536초였고 나머지 묶음은 owner 준비와 정리를 포함해 43.756초였다.

- 제품마다 별도 트랙을 만들고 현재 카탈로그의 정확한 클래스 ID를 사용했다. host가 실제 로드한 각 파일을 서명 검증한 번들의 실행 파일과 대조했다.
- 전체 범위 23개에서 현재값 12,478개를 모두 읽었다. 각 제품에서 확인한 하나의 쓰기 가능 값은 개별 변경과 별도 읽기 뒤 정확히 돌아왔다.
- 이번 21개는 대표 변경 전과 원복 뒤 쓰기 가능 값 10,210개 전체가 일치했다. 이 비교는 한 대표값을 바꾼 뒤 대상과 다른 값까지 보존됐다는 뜻이다.

버전별 결과는 [23개 실제 삽입·대표값 근거](evidence/2026-11-20-fabfilter-actual-representative.json)를 참조한다. 이 묶음의 프리셋 동작은 0회였다.

## FabFilter 자체 프리셋의 공개 프로그램 경로

두 기준 제품의 공식 별도 검사에서 MIDI 이벤트 입력 버스 0과 프로그램 목록 0을 읽었다. 목록에 프로그램 슬롯 128개가 있으며 검사 당시 프로그램 이름은 비어 있었다. 공개 MIDI 매핑은 Bank Select MSB와 LSB에 각각 별도 ID를 반환했다. 프로그램 변경 제어는 127단계의 전용 파라미터를 공개한다. Studio Pro 쪽에서도 해당 ID를 확인했지만 같은 표시명이 여러 행에 있다. 이 정보로 실제 프리셋 번호나 성공을 추정하지 않는다.

다음에는 팩토리 프리셋 메뉴가 표시하는 번호와 옵션을 먼저 확인한다. 같은 제품에서 Bank Select와 Program Change가 의도한 인스턴스에 전달되는 것을 검증한다. 프리셋 이름과 파라미터 변화, 원복을 따로 기록한다. 이 경로가 닫히기 전까지 제조사 `.ffp`를 MCP가 직접 불러온 흔적으로 설명하지 않는다. 현재 검증된 적용 경로는 Studio Pro가 발급한 `.preset` 항목이다.

기존 CV, 그래프와 기타 내장 작업은 11월 18일의 28개 ID 기준으로 이어간다.

## 호스트 프리셋 23개 시험과 공개 병합

R3의 21개는 각 버전의 확인된 인스턴스에서 Studio Pro 프리셋을 고유 이름으로 저장했다. 저장 후의 전체 기준값을 독립 읽기로 확인했다. 대표값 한 개를 변경하고 별도 읽기로 변화가 있었는지 확인한 뒤, MCP에서 발급한 카탈로그 토큰과 인덱스로 프리셋을 한 번 불러왔다. 새 전체 읽기에서 쓰기 가능 값 10,210개가 모두 일치했다. 카탈로그 해제도 21개 모두 확인했다. 719개 요청, 시험별 경과 시간 합계 362.786초였다.

Twin 2 첫 시도는 선택된 악기 트랙이 필요하다는 읽기 거절에서 멈췄다. 쓰기 요청은 0개였다. 유한 CLI 작업으로 정확한 트랙을 선택하고 독립 읽기로 단일 선택을 확인한 새 연결에서 통과했다. One도 같은 선택 조건으로 통과했다. 남은 개선은 이 선택 작업을 이름 있는 MCP 도구로 제공하는 것이다.

앞선 두 시범 제품을 포함해 23개 전체를 시도했다. Studio Pro 프리셋은 22개가 통과했다. Pro-Q 4의 기존 내부 항목 1개 불일치는 해결 대기 상태다. 이 검증과 제조사 프리셋 목록·적용, 개별 쓰기 전수, Save/reopen, 실제 신호 검증은 별도 완료 조건이다. [호스트 프리셋 결과](evidence/2026-11-20-fabfilter-host-presets.json)에 버전별 근거를 정리했다.

R107은 그 정확한 비활성 상태를 새 곡에서 먼저 검증하고, 해제 후 각 설정과 접근 가능 상태가 모두 되돌아왔음을 확인했다. Phase Meter 설정과 슬롯 바이패스, 믹서와 타임라인, 프리셋 적용 이전 Pedalboard 빈 랙 28개와 쓰기 가능 값 22개가 일치했다. 요청 72회, 6.135초, 보호 파일 27개, 관리 파일 18개였다. 두 토큰을 해제했고 앱, owner, 곡을 저장 없이 종료했다. R107은 호스트 슬롯 바이패스의 실제 왕복으로 집계한다. 랙 편집과 오디오 신호는 남아 있다.

같은 통합 후보의 Twin 2.41 편집기에서 `(0/5) By Random Trance DJM`을 확인했다. 제조사 메뉴로 직접 적용한 독립 기준은 초기 쓰기 가능 값 1,019개 중 200개가 달랐다. `Default Sound` 재선택 후 당시 실제로 남은 `vstp1073741826` 한 값의 초기 비트를 복원했다. 새로운 두 전체 읽기에 1,019개가 일치했다. 실제 MCP 파트의 노트는 0개였고 재생 전 설정과 믹서가 유지됐다.

## R33 Pro-Q 4 이펙트가 있을 때 현재 악기의 출력 채널

별도 실제 8.1.1 곡에 공식 One과 Pro-Q 4 효과를 정확한 클래스로 넣었다. 소스 트랙을 독점 선택하고 현재 문서와 Pro-Q 4 인스턴스를 함께 검사한 비공개 CLI 후보 `229a88250b013ee5b9895107bb923a61fbdff15a`를 썼다. `instrumentOutput` 선택자에서 현재/양방향 끝까지 읽었을 때 One 한 개가 있었다. 이후 설치본 인스펙터 리소스와 네이티브 바인딩을 대조했다. 이 선택자는 연결된 악기의 출력 채널을 표시했고 트랙의 MIDI 목적지 목록은 별도 `outputDeviceList`다. 준비 48회·4.844초, 후보 읽기 1회·0.423초, 독립 확인 15회·2.543초였다. 양쪽 플러그인의 쓰기 가능 값 903개, 믹서와 타임라인이 그대로였다. 인스펙터의 `Out One`을 확인했지만 좌표 입력은 창을 지정하는 단계에서 거부됐다. 인스펙터 표시를 되돌리고 곡을 저장 없이 닫았다. 보호 파일 24개·관리 파일 18개와 owner 종료를 확인했다. 실제 효과 MIDI 대상 등록 조건과 다른 출력 메뉴가 있는지는 소스 분석을 계속한다.

## R34 Timeless 2의 개별 파라미터 첫 묶음

## R35 Timeless 2 변경·원복 해시 대조

R34 대상과 겹치지 않는 이름 있는 값 세 개를 같은 공식 VST3의 새 인스턴스에서 왕복했다. 전체 페이지로 초기 네이티브 해시 두 개를 대조했다. 변경 후 한 이름의 새로운 원시값, 정규화 비트와 표시 문자를 독립 읽기로 받아 전체 예상 해시를 계산했다. 호스트의 네이티브 해시와 새로운 전체 페이지가 그 예상과 같았다. 복원마다 독립 네이티브 읽기 두 개가 원래 해시와 일치했고 마지막 전체 페이지로 확인했다. 요청 83회·11.302초, 보호 파일 30개·관리 파일 18개와 저장 없이 종료를 확인했다. 이 제품 204/705개, 전체 2,070/12,455개를 확인했다. 더 큰 묶음에서 매 회 전체 변경 페이지를 줄이고 시작·간격·종료 전체 검사를 유지할 때의 시간을 이어서 잰다.

R61은 Pro-G 1.42 ARM64 공식 바이너리의 SDK 컨트롤러 저장 경로를 REA와 Ghidra로 대조했다. 격리 컨트롤러에서 해당 값은 150ms 뒤에도 유지됐고 전체 조회값이 복원됐다. 실제 호스트에서 같은 값이 기준으로 돌아오는 이유는 미확정이다. 다음 격리 단위에서 Steinberg SDK의 무샘플 파라미터 전달을 비교한다. 전체 쓰기 검증은 9,942/12,455개이며, 2,513개가 남았다.

## R145·R146 중첩 라우팅 편집기 확인

R145는 실제 Routing 화면에서 Splitter 두 개와 서로 다른 가지의 Mixtool 두 개를 확인했다. 35개 소유권 행과 연결 40개가 그대로였고, `Presets`와 `SideChain`의 동적 자식 수만 화면 상태에 따라 달랐다. CCL SDK 헤더로 ARM64의 뷰·아이템 모델 슬롯을 각각 컴파일해 확인했다. 25회, 앱 종료까지 241.6초, 보호 파일 79개·관리 파일 18개였다.

R146은 동일 인스턴스의 편집기 닫힘, 이펙트, Routing 세 상태를 조회했다. 이펙트 화면에서는 실제 뷰 탐색 한도에 도달했다. Routing을 열면 일반 DeviceEditor의 해당 인스턴스 해석은 `MissingEditor`였다. 믹서 67행과 그래프 35행의 객체 정체·소유권 연결은 유지됐다. 라우팅 모델 포인터와 오디오 연결은 확보하지 못했다. 다음 정적 단위에서 인서트 폴더의 Routing 컨트롤러가 연결되는 경로를 좁힌다. 29회·5.773초, 앱 종료까지 158.1초, 보호 파일 98개와 실행 파일 18개 복원을 확인했다. 두 곡 모두 저장하지 않았다.

PR #23은 main `d0ef47a`, PR #24는 main `f9fc2f5`로 병합됐다. 각 PR의 필수 검사와 병합 트리 일치를 확인했다.

## R63~R66 FabFilter 처리부와 Pro-L 제품군

R63은 격리한 Pro-G 1.42의 공개 SDK 처리부에 샘플 없는 파라미터 큐를 전달했다. 일반 `Threshold` 요청은 저장 상태의 한 바이트를 바꾸고 원복했다. `vstp1073741828`의 0.035 요청을 처리부는 읽었으며, 같은 ID의 출력 큐에 약 -0.4444444를 반환했다. 처리부 164바이트와 후속 컨트롤러 값은 기준과 같았다. REA/Ghidra로 앞서 확인한 컨트롤러 단독 저장과 실제 처리 과정의 차이를 보존한다. Studio Pro에서 처리부의 출력값을 적용하는 정확한 순서까지 입증하지 않았다.

R64 Pro-L과 R65 Pro-L 2는 실제 8.1.1에서 MIDI CC 각각 128개를 개별 변경·조회·복원했다. R64는 1,598회·110.469초, 앱 206.3초, 보호 파일 79개였다. R65는 1,598회·110.195초, 앱 178.0초, 보호 파일 82개였다. R66 Pro-L은 내부값 일곱 개를 더 검증했다. 마지막 `vstp1073741828`은 독립 조회 두 번에서 기준값이었다. 170회·15.833초, 앱 67.1초, 보호 파일 84개였다. 모두 관리 파일 18개와 곡을 저장 없이 닫았음을 확인했다.

Pro-L은 154/155, Pro-L 2는 160/168이다. FabFilter 전체 10,205/12,455개를 개별 검증했고 2,250개가 남았다. 이어서 Pro-L 2 내부값과 Pro-MB 가상 CC를 확인한다.

## R147 저장곡 라우팅 읽기

실제 8.1.1이 열어 표시한 같은 저장곡의 인서트 그래프를 `song_read`와 `song-read`로 읽었다. Splitter 두 개, Mixtool 슬롯 두 개와 합류 노드 두 개, 방향이 있는 연결 일곱 개의 결과가 일치했다. 실제 Routing 화면의 위쪽에서 두 Splitter와 두 Mixtool의 가지를, 아래쪽에서 두 합류점을 확인했다. 슬롯 이름과 UID는 저장된 실제 삽입 항목에 연결했다. 20회·3.940초, 앱 107.5초, 보호 파일 102개, 관리 파일 18개였다. 실제 오디오 재생과 체인 변경은 수행하지 않았다. 이 단위는 저장본 조회이며 실시간 그래프 모델과 편집은 기존 대기열에 있다.

## R67~R69 Pro-L 2·Pro-MB와 Twin 3 자체 프리셋

R67은 Pro-L 2 내부값 일곱 개를 추가 검증했다. 마지막 `vstp1073741828`은 기존 다섯 제품처럼 독립 조회에서 기준값이었다. 170회·16.047초, 앱 102.2초, 보호 파일 86개였다. 개별 검증은 167/168개다. R68은 Pro-MB의 MIDI CC 128개를 각각 검증했다. 1,617회·117.709초, 앱 225.3초, 보호 파일 88개였다. 279/287개다. 두 시험의 실행기와 관리 파일 18개는 유지됐으며 곡을 저장하지 않았다.

R69는 official Twin 3 VST3 패키지와 일치하는 `Ambient Mover`를 공개 컨트롤러 `setState`에 전달했다. 초기 편집부 헤더 버전 3·1,228바이트, 프리셋 헤더 버전 18·5,758바이트였다. 편집부는 파일을 읽고 거절했으며 1,510개 컨트롤러 값과 5,224바이트 처리부 상태는 유지됐다. 격리 실행 0.799초였다. 기존 제조사 MIDI 프로그램과 Studio Pro 프리셋의 실제 적용 결과는 유지한다. FabFilter는 총 10,340/12,455개, 내부값 2,115개가 남았다.

[PR #25](https://github.com/dev-universe/fender-studio-pro-mcp/pull/25)는 필수 검사 두 개가 통과한 동일 트리로 main `8a04bef`에 병합했다. R147 저장곡 기능 [PR #26](https://github.com/dev-universe/fender-studio-pro-mcp/pull/26)은 로컬 Rust 216개, 브리지 419개와 Python 560개를 통과했다. PR #25의 문서 변경을 반영한 뒤 실행 소스가 그대로임을 확인했고 GitHub의 새 필수 검사 결과는 대기 중이다.

## R148 라우팅 팝업의 실제 컨트롤러

전용 곡에서 편집기 닫힘, 이펙트 편집기, Routing 화면을 순서대로 확인했다. `ApplicationWindow`의 `Workspace`는 유지됐다. 팝업 컨트롤러는 일반 편집기에서 `DeviceEditor`, Routing에서 `AudioFXCombinator`였고 두 경우 모두 선언된 노드 인터페이스가 있었다. 동일 세션·곡·인스턴스의 믹서 67행과 그래프 35행의 소유 관계를 대조했다. 29회·5.824초, 앱 121.3초, 보호 파일 108개와 관리 파일 18개 원복이었다. 곡을 저장하지 않았다. 다음에는 현재 인서트 폴더에서 이미 확보한 Combinator와 라우팅 컨트롤러의 정체가 일치하는지 확인한다.

요청한 한국어 소개와 줄바꿈은 별도 [README PR #27](https://github.com/dev-universe/fender-studio-pro-mcp/pull/27)에 올렸다. 최신 main 기준 필수 검사를 진행한다.

## R149·R150 실제 라우팅 객체와 체인 캡처

R149는 Routing 팝업의 `AudioFXCombinator` 정체를 정확한 `AudioInsertFolder` 아래에서 확보한 `Combinator`와 일치시켰다. 그 객체에서 `RoutingModel`이라는 직접 자식은 보이지 않았고, 발견한 뷰 인터페이스의 정체가 부모 화면에 연결된 뷰와 다르게 나왔다. 모델 추측 없이 중단했다. 앱 90.0초, 29회·5.835초, 보호 117개, 관리 파일 18개 원복이었다.

R150은 현재 폴더의 체인을 정상 `insert_chain_state`로 한 번 캡처했다. MCP 발급 해시와 파일 정체를 대조한 2,859바이트의 임시 파일 안에서 `fxgraph.xml`의 노드 여섯 개와 방향 연결 일곱 개를 확인했다. `presetparts.xml`의 파트 두 개를 각각 노드의 슬롯 ID·인덱스에 연결했고 R147의 두 Splitter, Mixtool 두 갈래와 합류점 두 곳이 일치했다. 캡처를 해제했고 파일이 사라졌다. 13회·2.045초, 앱 62.4초, 보호 121개와 관리 18개였다. 두 곡 다 저장하지 않았다. 다음 후보는 `include_routing`을 지정한 캡처에만 이 정보를 넣고, 일반 캡처와 복원·해제는 현재 형식을 유지한다.

R70은 실제 Pro-MB 내부값 일곱 개를 검증했다. 마지막 `vstp1073741828`은 독립 조회에서 원래 값이었다. 215회·20.408초, 앱 177.1초, 보호 91개·관리 18개였다. Pro-MB는 286/287이고 FabFilter 전체는 10,347/12,455개, 2,108개 남았다. 다음은 Pro-Q 2다.

R147 저장곡 조회 [PR #26](https://github.com/dev-universe/fender-studio-pro-mcp/pull/26)와 한국어 소개 [PR #27](https://github.com/dev-universe/fender-studio-pro-mcp/pull/27)은 둘 다 필수 검사 두 개를 통과해 병합됐다. `main`은 `0b5434a`이며 README 실제 GitHub 렌더링에서 요청 문구와 줄바꿈 한 번을 확인했다.
